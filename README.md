# clickhouse-jalali-date

> تبدیل تاریخ جلالی (شمسی) به میلادی و برعکس در **ClickHouse** با استفاده از SQL User-Defined Functions — بدون هیچ وابستگی خارجی.

<div dir="rtl">

مجموعه‌ای از توابع خالص ClickHouse (SQL UDF) برای تبدیل تاریخ بین تقویم جلالی/شمسی و گریگوری/میلادی. این توابع نیازی به افزونه، کتابخانه یا کد خارجی ندارند و کاملاً داخل موتور ClickHouse اجرا می‌شوند؛ بنابراین می‌توانید آن‌ها را مستقیماً در `SELECT`، `WHERE`، `GROUP BY` و `ORDER BY` به‌کار ببرید.

</div>

## ✨ ویژگی‌ها

- ✅ تبدیل **میلادی → جلالی** با تابع `pdate`
- ✅ تبدیل **جلالی → میلادی** با تابع `gdate`
- ✅ پشتیبانی از سال‌های **کبیسه** (هم تقویم میلادی و هم چرخه ۳۳ساله جلالی)
- ✅ خالص SQL — بدون وابستگی به Python / UDF سفارشی / باینری خارجی
- ✅ قابل استفاده در هر جای کوئری (`WHERE`, `GROUP BY`, اندیس‌ها و …)
- ✅ خروجی استاندارد `YYYY-MM-DD`
- ✅ بازهٔ آزموده‌شده: تمام روزهای `1900-01-01` تا `2123-12-31`
- ✅ رد تاریخ نامعتبر؛ عدم تبدیل بی‌صدای آن به روز یا ماه بعد

## اصلاح کنترل محدودهٔ تاریخ — ۲۰۲۶/۰۹/۲۳

روی ClickHouse `25.8.29.51`، بهینه‌ساز `optimize_time_filter_with_preimage` شرط مستقیم `toYear(DateTime) > 2123` را برای ستون غیرثابت به مقایسه با timestamp خارج از ظرفیت `DateTime` تبدیل می‌کرد؛ حتی تاریخ صحیح ۲۰۲۵ هم رد می‌شد. تستِ مقدار ثابت این مشکل را آشکار نمی‌کرد.

در `pdate`، سال پیش از مقایسه صریحاً به `Int64` تبدیل شده است تا کنترل محدوده عددی بماند. الگوریتم تبدیل، بازهٔ مجاز، timezone و رفتار nullable تغییر نکرده‌اند؛ تنظیم بهینه‌ساز نیز خاموش نشده است.

تست جدید [tests/test_datetime_regressions.py](tests/test_datetime_regressions.py) شامل ۱۰۶ بررسیِ ستون‌های `Date`، `Date32`، `DateTime` و `DateTime64`، مقدار تهی، دو timezone، مرز نوروز، رد تاریخ نامعتبر و فیلتر/گروه‌بندی ماهانه با بهینه‌ساز روشن و خاموش است. همین تست روی نسخهٔ معیوب شکست خورد و پس از اصلاح، هم روی SQL محلی و هم روی تابع نصب‌شده موفق شد.

## اصلاحات ۲۰۲۶/۰۹/۲۲

اصلاح جدول‌های طول ماه و مرز اسفند:

1. در `pdate_gdm` طول ماه‌های June، July، September، October، November و December اشتباه بود. جدول اصلاح شد؛ محاسبهٔ شمارهٔ روز میلادی در `pdate_gdn` اکنون از `dateDiff` خود ClickHouse استفاده می‌کند تا طول ماه و کبیسهٔ قرن‌ها دستی محاسبه نشوند.
2. بهمن اشتباهاً ۲۹روزه تعریف شده بود. طول آن **۳۰** روز است و شروع اسفند در اندیس **۳۳۶** سال قرار دارد، نه ۳۳۵. استخراج ماه/روز و محاسبهٔ معکوس `pdate_jdn` هر دو اصلاح شدند.
3. تاریخ‌هایی مثل `1404-12-30`، `1405-07-31` و رشتهٔ بدفرمت حالا خطای مشخص می‌دهند؛ `1403-12-30` که معتبر است پذیرفته می‌شود.
4. خروجی `gdate` از **`Date` به `Date32`** تغییر کرده تا تاریخ قبل از ۱۹۷۰ خراب نشود. این تغییر نوع را در کلاینت‌ها و ستون‌های مقصد بررسی کنید.
5. محاسبات میانی با lambda نگه داشته می‌شوند تا تکرار توابع در یک کوئری، درخت عبارت بسیار بزرگی نسازد. شکل کوئری تقویمی‌ای که قبلاً با محدودیت اندازهٔ درخت مواجه می‌شد، اکنون تست شده است.
6. الگوریتم ۳۳ساله حفظ شده اما دامنهٔ آن بی‌نهایت نیست: در بررسی مستقل، از `2124-03-20` اختلاف مشاهده شد. برای جلوگیری از خروجی نادرست، API عمومی فقط بازهٔ آزموده‌شدهٔ ۱۹۰۰ تا پایان ۲۱۲۳ را قبول می‌کند.

| ورودی میلادی | خروجی اشتباه قبلی | خروجی اصلاح‌شده |
|---|---|---|
| `2025-10-04` | `1404-07-13` | `1404-07-12` |
| `2026-03-20` | `1404-12-30` | `1404-12-29` |
| `2025-03-20` | `1403-12-31` | `1403-12-30` |

**اصلاح فایل، نصب روی سرور نیست.** تست‌ها بدون جایگزینی هیچ تابع نصب‌شده‌ای اجرا می‌شوند.

## 📦 نصب

فایل [pdate.sql](pdate.sql) تعریف همهٔ توابع را دارد. اجرای آن با `CREATE OR REPLACE FUNCTION`، توابع هم‌نام سرور را **جایگزین می‌کند**؛ قبل از اجرا نسخهٔ قبلی را نگه دارید و تغییر نوع خروجی `gdate` را بررسی کنید. نصب چند تابع اتمیک نیست؛ فایل کامل را در پنجرهٔ نگهداری، بدون کوئری تحلیلی هم‌زمان اجرا کنید.

### روش ۱ — از طریق `clickhouse-client`

```bash
clickhouse-client --multiquery < pdate.sql
```

### روش ۲ — از طریق فایل

```bash
clickhouse-client --multiquery --queries-file pdate.sql
```

### قبل و بعد از نصب

```sql
-- تعریف‌های قبلی را برای بازگشت احتمالی ذخیره کنید.
SELECT name, create_query
FROM system.functions
WHERE name = 'gdate' OR name = 'pdate' OR startsWith(name, 'pdate_')
ORDER BY name;
```

> توابع پس از اجرا روی سرور ذخیره می‌شوند و در همه‌ی session‌ها قابل استفاده‌اند.

اصلاح تابع، ستون‌های شمسیِ از قبل محاسبه‌شده، پارتیشن‌ها، materialized viewها یا خروجی‌های ذخیره‌شده را خودکار اصلاح نمی‌کند. اگر از نسخهٔ قبلی ساخته شده‌اند، بازبینی و بازسازی کنترل‌شدهٔ جداگانه لازم است؛ این مخزن هیچ backfill یا تغییری در دادهٔ کسب‌وکار اجرا نمی‌کند.

## 🚀 استفاده

### تبدیل جلالی به میلادی

ورودی یک رشتهٔ غیرتهی با ارقام ASCII و فرمت دقیق `YYYY-MM-DD` است و خروجی `Date32` میلادی است. مقدار `NULL`، فاصلهٔ اضافی و تاریخ نامعتبر رد می‌شوند:

```sql
SELECT gdate('1405-01-01') AS toGregorian;
-- 2026-03-21
```

### تبدیل میلادی به جلالی

ورودی `Date`، `Date32`، `DateTime` یا `DateTime64` است و خروجی یک رشتهٔ `YYYY-MM-DD` جلالی است. ورودی nullableِ تهی، خروجی `NULL` دارد:

```sql
SELECT pdate(now()) AS toJalali;
-- تاریخ واقعی زمان اجرای کوئری، نه یک مقدار ثابت

SELECT pdate(toDate('2026-03-21')) AS toJalali;
-- 1405-01-01

-- تابع timezone را حدس نمی‌زند. برای روزِ کسب‌وکار ایران:
SELECT pdate(toTimeZone(now(), 'Asia/Tehran'));
```

### استخراج سال / ماه / روز جلالی

```sql
SELECT
    splitByChar('-', pdate(today()))[1] AS jalali_year,
    splitByChar('-', pdate(today()))[2] AS jalali_month,
    splitByChar('-', pdate(today()))[3] AS jalali_day;
```

## 🧪 نمونه‌های کاربردی

| ورودی | کوئری | خروجی |
|---|---|---|
| تاریخ جاری | `SELECT pdate(now())` | تاریخ زمان اجرای کوئری |
| `2026-03-21` (نوروز) | `SELECT pdate(toDate('2026-03-21'))` | `1405-01-01` |
| اول فروردین ۱۴۰۵ | `SELECT gdate('1405-01-01')` | `2026-03-21` |
| ۱۴۰۵/۱۲/۲۹ | `SELECT gdate('1405-12-29')` | `2027-03-20` |

### فیلتر کردن بر اساس ماه جلالی

```sql
SELECT *
FROM orders
WHERE splitByChar('-', pdate(created_at))[2] = '01';  -- فقط فروردین
```

## 📚 مرجع توابع

### توابع اصلی (Public API)

| تابع | امضا | خروجی | توضیح |
|---|---|---|---|
| `pdate` | `pdate(gdate)` | `String` | تبدیل تاریخ میلادی به جلالی (`YYYY-MM-DD`) |
| `gdate` | `gdate('jdate')` | `Date32` | تبدیل رشتهٔ معتبر تاریخ جلالی به میلادی |

### توابع کمکی (داخلی)

| تابع | توضیح |
|---|---|
| `pdate_gdn(gdate)` | محاسبه‌ی «شماره‌ی روز» میلادی (شمارش روز از سال ۱۶۰۰ میلادی) |
| `pdate_jdn(jy, jm, jd)` | محاسبه‌ی «شماره‌ی روز» جلالی از سال/ماه/روز |
| `pdate_jy(gdn)` | استخراج **سال** جلالی از شماره‌ی روز |
| `pdate_jm(j3)` | استخراج **ماه** جلالی (۱ تا ۱۲) |
| `pdate_jd(j3)` | استخراج **روز ماه** جلالی (۱ تا ۳۱) |
| `pdate_j3(gdn)` | اندیس روز در داخل سال جلالی |
| `pdate_gdm(i)` | تعداد روزهای هر ماه میلادی (۰ تا ۱۱) |
| `pdate_jdm(i)` | تعداد روزهای هر ماه جلالی (۰ تا ۱۱) |
| `pdate_gdate_checked(jy, jm, jd)` | اعتبارسنجی تاریخ و بازهٔ تبدیل معکوس |

> توابع کمکی API اعتبارسنجی‌شدهٔ عمومی نیستند. `pdate_gdm` و `pdate_jdm` طول ماه در سال عادی را می‌دهند؛ اعتبار اسفندِ کبیسه در تبدیل اصلی با سال بررسی می‌شود.

## ⚙️ نکات فنی

- **الگوریتم:** چرخهٔ ۳۳ساله، با دامنهٔ محدود و آزمون مستقل؛ نه ادعای صحت نجومی برای تمام قرن‌ها.
- **بازهٔ عمومی:** میلادی `1900-01-01` تا `2123-12-31`، متناظر با شمسی `1278-10-11` تا `1502-10-10`. همهٔ سال‌های ۱۳۰۰ تا ۱۵۰۰ شمسی را پوشش می‌دهد.
- **نوع داده:** برای تاریخ‌های قدیمی از `Date32` استفاده کنید. تبدیل زودهنگام به `Date` یا ساختن `Date32` خارج از دامنهٔ خود ClickHouse ممکن است ورودی را پیش از رسیدن به این تابع تغییر دهد؛ تابع نمی‌تواند متن اصلیِ از دست‌رفته را بازیابی کند.
- **سازگاری آزموده‌شده:** ClickHouse `25.8.29.51`؛ نسخه‌های دیگر را با تست همراه مخزن بررسی کنید. تضمین قبلیِ آزمون‌نشده برای ۲۱.۸ حذف شده است.
- **Timezone:** روز از timezone خود مقدار `DateTime`/`DateTime64` گرفته می‌شود؛ برای تهران صریحاً `toTimeZone` استفاده کنید.

مستندات مرجع: [SQL UDF](https://clickhouse.com/docs/reference/statements/create/function)، [WITH و lambda](https://clickhouse.com/docs/reference/statements/select/with)، [نوع Date32](https://clickhouse.com/docs/reference/data-types/date32).

## آزمون بدون نصب یا تغییر سرور

تست [tests/test_pdate.py](tests/test_pdate.py) **همین فایل SQL** را به lambdaهای محلی با نام متفاوت در یک `WITH … SELECT` تبدیل می‌کند. اتصال `readonly=1` است؛ نه `CREATE` اجرا می‌شود، نه جدول کسب‌وکار خوانده یا نوشته می‌شود. تعریف توابع نصب‌شده قبل و بعد از تست مقایسه می‌شود.

پیش‌نیاز تست: Python با `clickhouse-connect`، و Node دارای تقویم Persian در ICU. این‌ها فقط برای تست‌اند؛ خود توابع نصب‌شده وابستگی خارجی ندارند.

```bash
# اطلاعات اتصال را از محیط/مدیریت امن رمزها تنظیم کنید؛ رمز را داخل فایل نگذارید.
# CLICKHOUSE_HOST, CLICKHOUSE_PORT, CLICKHOUSE_USER, CLICKHOUSE_PASSWORD
# برای HTTPS: CLICKHOUSE_SECURE=1
python -B tests/test_pdate.py

# پس از نصب: اجرای همان تست‌ها روی خود توابع نصب‌شده، بدون تغییر آن‌ها
python -B tests/test_pdate.py --installed
```

مرجع مستقل [tests/persian_oracle.mjs](tests/persian_oracle.mjs) از `Intl`/ICU استفاده می‌کند، نه الگوریتم SQL همین پروژه. اجرای ثبت‌شده با Node `23.11.0` / ICU `77.1`:

- تمام **۸۱٬۸۱۴ روز** بازه با مرجع مستقل تطبیق داشتند.
- تمام **۸۱٬۸۱۴ تبدیل رفت‌وبرگشت** دقیق بودند.
- **۴۸ بررسی ورودی نامعتبر** با تنظیم short-circuit روشن و خاموش، رد صحیح داشتند.
- انواع تاریخ، timezone، nullable، کبیسه‌ها، تاریخ قبل از ۱۹۷۰ و کوئری چندبار استفاده از تابع بررسی شدند.
- در خود تست‌ها، نوشتن در دیتابیس و تغییر تابع نصب‌شده: **صفر**؛ نصب تابع مرحله‌ای جدا از تست است.

جزئیات اجرای آخر و هش فایل آزموده‌شده در [TEST_RESULTS.md](TEST_RESULTS.md) آمده است.
